## 0. Mission

Build a **runnable, demonstrable prototype** of the *APAAR-Based Student Data Management and Verification System* (Smart India Hackathon problem statement SIH26263, AICTE). The architecture is already decided and documented in `docs/SIH26263_Architecture_Blueprint.pdf`; your job is to implement roughly 40–50% of it as **complete vertical slices** (UI → API → database → tests) that make three end-to-end demos work flawlessly.

Do not redesign the architecture. Do not stop to ask for approval between phases. Ask only if you hit a genuine blocker. Keep a checklist in `docs/BUILD_LOG.md` and update it as you finish each phase.

### Non-negotiable rules
1. **Synthetic data only.** No real people, institutions or APAAR IDs. Synthetic APAAR IDs are 12 digits starting with `9`.
2. **APAAR verification is simulated** against a synthetic registry table. Every API result and UI label that shows an APAAR check must say `SIMULATED`. Never invent an "official APAAR API".
3. A well-formed APAAR ID is **not** proof of identity. Format check and registry check are separate rules.
4. A flag means "a person should look". **Never label anything fraud.** Nothing is auto-resolved except a capacity flag whose measured condition disappears (logged as a system event, reopenable).
5. Never hard-delete student, enrolment, issue or credential records. Changes create revisions with a reason.
6. No blockchain, microservices, Kubernetes or ML models.
7. **Never claim a test passed unless you ran it and saw it pass.** Report real numbers.
8. Every dashboard number must come from the database. No hard-coded charts, no dead buttons.

## 3. Seat-counting rules (the definition of "excess") — implement as a pure function and unit-test it

1. Only enrolments with status `ACTIVE` or `PROVISIONAL` occupy a seat.
2. `REGULAR` and `NRI` count against `approved_intake`.
3. Each supernumerary category (`SN_FN_OCI`, `SN_CIWG`, `SN_TFW`, `SN_OTHER`) counts only against its own cap.
4. Unused supernumerary seats are **not transferable** between categories.
5. Default caps (rounded **down**), stored with `rule_source`:
   - FN/OCI/CIWG pool = 15% of intake for (ENGINEERING, DIPLOMA|UG), 25% for (ENGINEERING, PG) and for all other disciplines. CIWG cap = pool // 3, FN/OCI cap = pool − CIWG.
   - TFW cap = floor(5% of intake). SN_OTHER cap = 0 unless configured.
   - Check: intake 60 UG engineering → FN/OCI 6, CIWG 3, TFW 3. Intake 60 PG management → 10, 5, 3. Intake 10 UG engineering → FN/OCI 1, CIWG 0, TFW 0.
6. `excess_over_intake = max(0, (REGULAR+NRI) − approved_intake)`; category excess = `max(0, enrolled − cap)`.

`position_from_counts(intake, caps, counts)` returns: approved_intake, within_intake_enrolled, regular, nri, excess_over_intake, vacant_within_intake, utilisation_pct (None if intake 0), supernumerary{cat:{enrolled,cap,excess}}, supernumerary_enrolled, total_enrolled, any_excess.

Allowed status transitions: PROVISIONAL→{ACTIVE,CANCELLED,WITHDRAWN}; ACTIVE→{WITHDRAWN,TRANSFERRED_OUT,GRADUATED,CANCELLED}; WITHDRAWN→{ACTIVE}; others terminal. Every change needs a reason and the current `version` (409 on mismatch), writes a revision and re-runs capacity checks.

## 4. Validation engine — 25 rules, stable IDs (seed into `validation_rules`)

Template columns: `apaar_id, institution_student_id, full_name, date_of_birth, gender, nationality_status, citizenship_country, programme_code, academic_year, seat_category, admission_date, social_category, email, apaar_pending_reason`. Accept dates `YYYY-MM-DD`, `DD-MM-YYYY`, `DD/MM/YYYY`. Gender M/F/T/O. `PIO` maps to `OCI`. Header aliases (e.g. `roll_no`, `dob`) accepted.

| ID | Sev | Condition |
|---|---|---|
| R001_REQUIRED | ERROR | required column empty (all except apaar_id, citizenship_country, social_category, email, apaar_pending_reason) |
| R002_FORMAT | ERROR | bad date / enum / email / year format |
| R003_APAAR_MISSING | ERROR | no APAAR ID and no pending reason |
| R004_APAAR_PENDING | REVIEW | no APAAR ID with reason FOREIGN_NATIONAL / APPLIED_AWAITING_ID / OTHER_DOCUMENTED (FOREIGN_NATIONAL only valid for FN/OCI → else R013) |
| R005_APAAR_FORMAT | ERROR | not exactly 12 digits, or one repeated digit (no invented checksum) |
| R006_APAAR_NOT_FOUND | ERROR | adapter NOT_FOUND / INACTIVE |
| R007_APAAR_MISMATCH | REVIEW | adapter NAME_MISMATCH / DOB_MISMATCH |
| R008_APAAR_UNVERIFIED | WARNING | adapter UNAVAILABLE (store as UNVERIFIED) |
| R010_DATE_LOGIC | ERROR | DOB or admission date in future; age at admission < 15 (skip age calc if DOB in future) |
| R011_DATE_UNUSUAL | WARNING | age > 45, or admission date outside 1 May (start year) – 31 Mar (next year) |
| R012_PROGRAMME | ERROR | programme code not this institution's, or no approved intake for the year |
| R013_CATEGORY_CONSISTENCY | ERROR | SN_FN_OCI needs FN/OCI; NRI seat needs NRI; SN_CIWG needs INDIAN/NRI; FN needs non-India citizenship; INDIAN/NRI with non-India citizenship |
| R014_YEAR_MISMATCH | ERROR | row year ≠ upload year |
| F001_DUP_APAAR_IN_FILE | ERROR | same APAAR on >1 row (flag every copy, cite the other row numbers; spreadsheet row = index+2) |
| F002_DUP_ROLL_IN_FILE | ERROR | same roll number on >1 row |
| F003_POSSIBLE_DUP_IN_FILE | WARNING | same name_key + DOB with different APAAR IDs |
| F004_REPEATED_FILE | WARNING | same file SHA-256 uploaded before by this institution |
| D001_EXISTING_RECORD | WARNING | will update an existing enrolment (history kept) |
| D002_ROLL_CONFLICT | ERROR | roll number already belongs to a different student here (include `enrolment_id` in evidence) |
| D003_XINST_ACTIVE | REVIEW | APAAR has ACTIVE/PROVISIONAL enrolment at another institution |
| D004_ATTR_CONFLICT | REVIEW | APAAR on file with different name/DOB — **master record not overwritten** |
| D005_POSSIBLE_DUP_IDENTITY | REVIEW | identity resolution finds a high-score candidate with a different/absent APAAR (exclude the matched student itself) |
| C001_EXCESS_INTAKE | REVIEW | aggregate: within-intake > approved intake |
| C002_SUPERNUMERARY_CAP | REVIEW | aggregate: a category over its cap |

Severity semantics: ERROR blocks commit of that row; WARNING commits with a note; REVIEW commits and opens a `validation_issue`. Excess-intake rows are **accepted** (blocking would reward under-reporting) and flagged. AICTE can toggle rules/severities via API; `R001, R002, D002, F001, F002` are locked (409).

Every finding: `{rule_id, severity, field, message, evidence, suggestion?}`. Pipeline order: normalise → row rules → adapter → file rules → repository rules (skip repository rules if R001/R002/R005/R006/R012 errors) → projection.

**Pitfalls already found while validating this design — handle them:**
- Pending-APAAR student re-submitted later (same roll, same name_key + DOB, student has no APAAR): treat as the *same* student (update, attach the new APAAR ID with a revision), not D002.
- When correcting a committed record, filter out findings about itself (D001, D004, D002 whose enrolment_id is itself, D005 whose only candidate is itself).
- SQLAlchemy: don't `merge()` two pending objects with the same PK before a flush (UNIQUE error).
- Error responses: put `row_status` (not `status`) in error detail so it doesn't overwrite the HTTP status field.

## 5. Innovation features (these are what make the demo stand out — build them)

### 5.1 Seat ledger + seat-check (prevention, not only detection)
- `POST /api/v1/seat-check {programme_code, academic_year, seat_category, count}` → `{allowed_within_rules, counts_against: "approved intake"|"<category> cap", within_intake:{approved,occupied,after}, category:{cap,occupied,after}, message}`. Advisory only; log to `seat_check_logs`; available to institution users and ERP clients (scope `seat:check`).
- Import preview shows a **projection** per programme: current vs after-commit position, with a red line "Committing will exceed approved capacity. Records are still accepted and AICTE is flagged."

### 5.2 Live updates
- `GET /api/v1/events` (Server-Sent Events, auth via short-lived query token or cookie). Emit `seat.changed {programme_id, position}` and `issue.opened/updated` after commit, status change, correction and issue actions — **scoped**: institutions only receive their own events; AICTE receives all. Dashboards update without reload (show a small "updated just now" marker).

### 5.3 Indian-name-aware identity resolution (`identity.py`)
- `name_key`: NFKD → ASCII, lowercase, letters only, tokens sorted.
- Phonetic fold per token: `aa→a, ee→i, oo→u, th→t, dh→d, bh→b, kh→k, ph→f, w→v, z→j`, collapse doubled letters, drop trailing `h`.
- Initial compatibility: a single-letter token matches any token starting with it.
- Blocking: candidates share DOB, or DOB with day/month swapped.
- Two tokens are *equivalent* if equal after the phonetic fold or Jaro–Winkler ≥ 0.92 (so `subramaniam` ≈ `subramanian`).
- Weights (log-likelihood style, document them): exact token-set +6; all tokens equivalent +4.5; initial-compatible +3; partial overlap +2 per shared token; DOB exact +4, swapped +1.5; gender agree +1, disagree −3; different APAAR IDs both present −2; linked by recorded transfer −2. Score ≥ 9 → D005 REVIEW; 6–9 → list in `identity_candidates` only.
- Store weights per pair and show them in the UI ("Why we think these match"). Reviewer decision SAME_PERSON / DIFFERENT_PEOPLE; never auto-merge.

### 5.4 Guided correction
- **Did-you-mean APAAR:** for R006, generate all single-digit substitutions (108) and adjacent transpositions (11) of the ID; query the adapter; if **exactly one** variant matches the row's name_key and DOB, attach `suggestion: {field:"apaar_id", value:"…", reason:"matches name and date of birth"}`. UI shows an "Use this" button. Never auto-apply.
- **Bulk fix:** `POST /imports/{id}/bulk-fix {field, from, to}` updates every uncommitted row where `data[field]==from`, then re-validates.
- **Excel template:** `GET /imports/template.xlsx` with drop-downs (data validation) for gender, nationality_status, seat_category, apaar_pending_reason and the institution's own programme codes.

### 5.5 Peer-group review priority (`analytics.py`)
Per institution-year: rule signals — seats over intake (min(35, 10 + 100×excess/intake)), supernumerary over cap (min(15, 5+2×excess)), open cross-institution conflicts (min(20, 4×n)), unverified-APAAR share >5% (min(15, round(30×share))), uncorrected upload error share >10% (min(10, round(20×share))), enrolment jump >30% with intake change ≤10% (10), changes after submission declared (min(10, 2×n)). Plus **peer statistics**: robust z = (x − median)/(1.4826×MAD) vs peers of same institution_type (fallback national if <8 peers; with only 5 seeded institutions, use all institutions and say so) on utilisation, supernumerary share, NRI share, out-of-window admission share, max same-DOB share; |z| > 3.5 adds 8 points with sentence "utilisation 113% vs peer median 88%". Score cap 100; bands LOW <25, MEDIUM 25–49, HIGH ≥50. Always show the disclaimer: *"Ranks institutions for review attention. A high score is not evidence of wrongdoing."*

### 5.6 Selective-disclosure credentials (SD-JWT style)
- Ed25519 key generated on first start into `var/` (0600); `kid = "ed25519-" + sha256(pub)[:16]`; publish JWKS at `/.well-known/issuer-keys`.
- Payload (W3C VC 2.0 shape): `@context`, `type ["VerifiableCredential","StudentEnrolmentRecord"]`, `id urn:uuid:<cred id>`, issuer, validFrom/validUntil (+365 d), `credentialStatus.id → /api/v1/verification/credentials/{id}`, and `credentialSubject._sd: [sha256 digests]`.
- Disclosures: for each claim (`apaarId, name, institutionStudentId, institution, aicteInstitutionCode, programme, admissionYear, enrolmentStatus`) create `base64url(JSON([salt16, claim, value]))`; digest = base64url(sha256(disclosure)).
- Token = `<header>.<payload>.<sig>~<disclosure>~<disclosure>~…` (compact JWS header `{"alg":"EdDSA","typ":"vc+sd-jwt","kid":…}`).
- Verification checks, in order, each reported as pass/fail with a sentence: structure, known key, signature, every presented disclosure's digest is in `_sd`, validity period, status (ACTIVE / REVOKED with reason / SUPERSEDED), currency note if enrolment status changed after issuance. Return only disclosed claims; mask APAAR as `XXXX-XXXX-1234` unless the holder disclosed it.
- Student UI: tick-boxes choose which claims to share → copy token / show QR. Verifier page has **"Demo: tamper with this record"** (edits a disclosed value or the payload without re-signing) to show failure.
- Issue: INST_ADMIN only, enrolment ACTIVE/GRADUATED, student has APAAR. Re-issue supersedes. Revoke: INST_ADMIN (own) or AICTE_ADMIN, reason required.
- Certificate view `GET /credentials/{id}/certificate` (HTML, printable): shows **institution student ID next to APAAR ID** (requirement 10), QR to `/#/verify?cid=…`, watermark "SAMPLE · SYNTHETIC DATA".

### 5.7 Consent-based verification
- Public `POST /verification/verify-token` (rate-limited, audited; presentation = consent).
- `POST /verification/requests` (VERIFIER): needs APAAR **and** DOB + purpose; response is identical whether or not it matched (`"If the details match, the student will be asked for consent"`); verifier sees NO_MATCH as pending. Student approves/declines; `GET …/result` returns 403 without consent, otherwise fixed minimal fields (name, masked APAAR, institutions, programmes, years, statuses, registry status with mode). Never DOB, nationality, category, contact.

### 5.8 Student correction requests
- Student: `POST /me/correction-requests {enrolment_id, field, requested_value, explanation}`. Institution queue page with due date; accept (opens the correction form pre-filled) or reject with note. Overdue requests count as a review-priority signal.

### 5.9 Privacy-preserving conflict view
- Cross-institution issue (D003) links both institutions. Institution users see their own enrolment in the evidence and the other side as *"Another AICTE-approved institution (identity withheld)"* with only status and year. AICTE and auditors see both.

### 5.10 Hash-chained audit
- `hash = sha256(prev_hash + canonical_json(event))`, genesis `"0"*64`. Record: login (success/denied), every create/update/status change/correction, import upload/correct/exclude/commit, issue actions, credential issue/revoke/verify, consent decisions, record views, report exports, rule changes, **every 403** (global exception handler). `GET /audit/verify-chain` returns first broken seq. Test: edit one row's detail → chain reports broken.

## 6. Security requirements
- Roles: AICTE_ADMIN, AICTE_ANALYST, INST_ADMIN, INST_STAFF, VERIFIER, AUDITOR, STUDENT (+ integration clients with scopes).
- Authentication ≠ authorization. Load the user from DB on each request; check role **and** institution scope on every route. Objects of another institution → **404** (not 403) so existence isn't disclosed; explicit cross-institution list filters → 403.
- HS256 bearer tokens (120 min), secret generated into `var/` if not in env. Login rate limit + lockout after 5 failures.
- Uploads: `.csv`/`.xlsx` only, magic-byte check for xlsx (`PK`), reject NUL bytes in CSV, 2 MB, 5,000 rows, header must contain required columns.
- CSV exports neutralise formula injection (prefix `'` for cells starting `= + - @`).
- Security headers: CSP (`script-src 'self'`), nosniff, frame deny, no-referrer, `Cache-Control: no-store` on API. Error shape `{"error":{"status","message","request_id",...}}`, never stack traces.
- APAAR masked for AICTE_ANALYST and everywhere outside the owning institution / AICTE_ADMIN. No partial APAAR search (exact 12 digits only).
- Integration API: `X-API-Key` (store only hash, show once), `Idempotency-Key` required; same key+body → stored response; same key, different body → 409.
- `.env.example` only; never commit secrets; `var/` in `.gitignore`.
